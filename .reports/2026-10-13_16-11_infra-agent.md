### packages/api
- `src/db/schema.ts` (modified):
  - Added `'infra'` to `agentTypeEnum`.
  - New pgEnums `resourceTypeEnum`, `resourceStatusEnum` and `deployStatusEnum`, built from the shared enums through an `enumValues()` helper so the DB and TypeScript can't drift. Drizzle 0.38 doesn't accept TS enum objects directly.
  - New tables, each with a `tenant_id` FK (cascade) and a tenant index:
    - `resources`: `updatedAt` uses `$onUpdate`.
    - `deployments`: FK to resources, cascade.
    - `secrets`: FK to resources, cascade; unique on `(tenant_id, resource_id, key)` for upsert.
    - `infra_events`: nullable resource FK, set null.
- `src/config/env.ts` (modified):
  - Added `RENDER_API_KEY` (from the spec).
  - Extra `RENDER_OWNER_ID`: Render requires an `ownerId` to create services.
  - Extra `SECRETS_ENCRYPTION_KEY`: 32 bytes in base64, and an empty string counts as unset.
- `src/integrations/render.ts` (created):
  - `RenderClient` is a typed `fetch` client for `https://api.render.com/v1` with bearer auth. It has all 18 methods from the spec. `createPostgres` is a Clerk-defaults wrapper over `createPostgresDb`.
  - Errors: `RenderApiError` (status, message, body) wraps both HTTP and network errors.
  - List responses are unwrapped into `{ items, cursor }`.
  - Also: `renderResourceName()` produces `clerk-tenant-{tenantId}-{slug}`, and the `renderClient` singleton is `null` when the key is unset.
  - Request and response shapes are written from Render's API docs from memory and only cover the fields Clerk uses. Check them against api-docs.render.com when wiring real calls.
- `src/integrations/render.test.ts` (created): 7 tests with mocked `fetch`: naming, bearer header, pagination, 4xx wrapping, network wrapping, missing owner id, empty 2xx body.
- `src/utils/crypto.ts` (created):
  - AES-256-GCM `encryptSecret` / `decryptSecret` and `SecretsNotConfiguredError`.
  - The ciphertext format is `iv.tag.ciphertext`, each part base64.
- `src/modules/resources/resources.types.ts` (created): zod `tenantParamsSchema` / `resourceParamsSchema`, re-exports of the shared body schemas, and `ResourceConflictError`.
- `src/modules/resources/resources.service.ts` (created):
  - Real Drizzle CRUD. **Every query filters by `tenant_id`.**
  - Each state change writes an `infra_events` row and publishes on the bus. The publish is fire-and-forget, so a Redis outage can't hang a request.
  - Create: status `requested`, cost computed, publishes `resource.requested`.
  - Delete: checks `assertTransition(→destroying)`, then a status-guarded update, then publishes `resource.destroyed`.
  - Deploy: only for deployable types (not Postgres or key-value) and only when the resource is `active`. Inserts a deployment row and publishes `deployment.triggered`.
  - Secrets: encrypted upsert inside a transaction. GET returns keys only.
- `src/modules/resources/resources.routes.ts` (created):
  - The 9 routes, mounted at `/api/tenants/:tenantId/resources`, behind `authenticate` plus `requireOwnTenant`. That second guard returns 403 when the path tenant isn't the JWT tenant.
  - Status codes: 400 for zod errors, 404 for missing resources, 409 for invalid state, 503 when secrets aren't configured, and 201/202 for create, delete and deploy.
- `src/index.ts` (modified): registers `resourcesRoutes`.
- `src/ws/socket.ts` (modified): all 8 infra events added to `RELAYED_EVENTS`.

### packages/agents
- `src/infra/index.ts` (created): `InfraAgent` subscribes to the 5 events in the spec.
  - `resource.requested` → `provision`, then publishes `provisioned` or `failed`.
  - `resource.destroyed` → `destroy`.
  - `deployment.triggered` → `deploy`, then publishes `completed` or `failed`.
  - `forecast.updated` → computes tenant cost and publishes `resource.cost.alert` when cost is more than 10% of the projected balance.
  - `resource.cost.alert` → log only, so the agent can't loop on its own alert.
- `src/infra/provisioner.ts` (created): the state machine logic is real, and the Render calls are stubs.
  - `transitionResource` is a status-guarded `UPDATE … WHERE tenant_id AND id AND status = from`, so duplicate events are no-ops. It writes an `infra_events` row.
  - `provision`, `destroy` and `deploy` handle every branch.
  - The stubs `provisionOnRender`, `destroyOnRender` and `deployOnRender` return null, so for now every provision **ends in `failed` with the reason "Render provisioning not implemented"**. Resources with no Render id are destroyed immediately.
- `src/infra/cost-tracker.ts` (created): `calculateResourceCost` and `calculateTenantCost`. Destroyed and failed resources are excluded.
- `src/infra/health-monitor.ts` (created): `checkResourceHealth` stub; for now health comes from the stored status.
- `src/infra/cost-tracker.test.ts` (created): 3 tests.
- `src/core/context.ts` (modified): exported a `query()` helper on the existing lazy pool. Its doc comment requires `tenant_id` in every statement.
- `src/config/env.ts` (modified): `RENDER_API_KEY` and `RENDER_OWNER_ID`.
- `src/index.ts` (modified): `InfraAgent` added to the factories map.
- `astropods.yml` (modified): `infra` pod.

- `TODO(dev)` items to decide:
  1. **Render client sharing:** `provisioner.ts` can't import `packages/api/src/integrations/render.ts`. Move `RenderClient` into `@clerk/shared` (it only needs `fetch`) or give agents a copy.
  2. **Event naming:** `resource.destroyed` (from the spec) is published when teardown is *requested*. Consider `resource.destroy_requested`, and publish `resource.destroyed` after teardown actually finishes.
  3. **Config updates:** pushing config changes to Render needs a `resource.update` event plus `active → updating → active` handling in the agent.
  4. **Cost alert threshold:** the 10% cutoff is hardcoded (`COST_ALERT_RATIO`). It should become a per-tenant rule.
- A resource in `requested` can't be deleted directly; the table goes `requested → failed → destroying`. While the provisioner is a stub, every resource fails right away, so they're all deletable.
